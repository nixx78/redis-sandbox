## Общая информация
Cache — это слой хранения данных для ускорения чтения и снижения нагрузки на дорогие ресурсы.
Основные цели:

### Уменьшение latency
Типичные задержки:
L1 cache (memory)   ~10–100 ns
Redis               ~0.5–1 ms
Database            ~5–100 ms
External API        ~50–500 ms

### Снижение нагрузки
без cache: 1000 requests → 1000 DB calls
с cache:   1000 requests → 1 DB call

### Стабилизация нагрузки
Cache сглаживает пиковые нагрузки.

### Повышение устойчивости
Позволяет пережить:
* медленную БД
* временную недоступность API
* сетевые задержки

## Основные случаи использования Cache
* часто читаемые данные
* редко изменяющиеся данные
* дорогие операции (DB / API / вычисления)
* одинаковые данные для многих пользователей

## Основные требования к cache

### Ограничение размера
Cache обязан иметь limit.
Причина:
без лимита → OutOfMemoryError

Примеры:
* maximumSize
* maximumWeight

### Должен быть установлен TTL
Cache должен автоматически очищаться
Причины:
* данные устаревают
* память должна освобождаться

Типы:
* expireAfterWrite
* expireAfterAccess

### Инвалидация
Должна быть возможность очистить cache при изменении данных.
Методы:
* cache evict
* explicit invalidate
* versioning

### Защита от cache stampede
Cценарий:
cache expired:  1000 requests -> 1000 DB calls

Решения:
* синхронная загрузка (sync)
* cache loader
* refreshAfterWrite
* distributed locks

### Мониторинг
Нужно отслеживать:
* hit rate
* miss rate
* evictions
* cache size
* latency

Формула:
    hitRate = hits / (hits + misses)
Обычно:
    хороший cache → hitRate > 80%

## Основные типы cache

### L1 cache (in-memory)

Примеры:
* Caffeine
* Guava

Плюсы:
* очень быстрый
* нет сетевых вызовов

Минусы:
* не общий между экземплярами

### L2 cache (distributed)
Примеры:
* Redis
* Memcached

Плюсы:
* общий для всех сервисов
* переживает рестарты

Минусы:
* медленнее памяти

## Основные проблемы кеширования

### Cache stampede
Массовый запрос к DB при истечении TTL.

Решения:
* single-flight loading
* sync cache
* refresh

### Stale data
Cache хранит устаревшие данные.

Решения:
* TTL
* explicit invalidation
* versioning

### Cache avalanche
Много ключей истекают одновременно.

Решения:
* случайный TTL (jitter)
* refresh
* постепенное обновление

### Hot key
Один ключ получает огромное количество запросов.

Решения:
* локальный cache
* replication
* request coalescing

### Cache penetration
Запросы к несуществующим данным.

Решения: 
* negative caching - это кеширование отрицательных результатов (например, когда данных нет, сохраняем - NULL)
* bloom filter - это очень компактная probabilistic структура данных, которая позволяет быстро проверить может ли ключ существовать в принципе

## Лучшие практики
* кешировать read-heavy операции
* использовать разумный TTL
* ограничивать размер cache
* мониторить hit rate
* использовать L1 + L2 cache при высокой нагрузке
* защищаться от stampede

## Типичные ошибки

* cache без TTL
* cache без ограничения размера
* кеширование слишком больших объектов
* кеширование mutable объектов
* отсутствие invalidation
* кеширование всего подряд
